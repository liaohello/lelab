# T2 wheel protocol candidate v1 — 2026-11-04

**Integration contract for offline development, not an assertion about any board.** The original firmware does not implement these messages. The companion C file is a standalone, unintegrated candidate; it must not be flashed. T1 may use `golden_vectors.json` to implement a decoder fixture. Availability, build, boot uniqueness, real sampling and watchdog must be established by a future integrated build and hardware verification.

## Transport and negotiation

Reuse original packet framing `AA 55 func len payload crc8`: function `0x0c` (the original enumeration has function values 0..11), one-byte payload length, Dallas/Maxim CRC-8 (reflected polynomial 0x8c, initial 0, no xor-out) over function, length and payload. `crc8("123456789") = a1`. All integers little-endian; floats IEEE-754 binary32 little-endian. Reject wrong header/function/length/CRC and unexpected message types before decoding. This function assignment is a **T2 interface proposal**, awaiting coordinator approval; it does not alter the section 3 logical fields.

Query payload `01` asks for capability response; this handler is **not yet wired**. A v1 capability response payload is `<BB16s16sI`: type `81`, major version `01`, 128-bit boot ID, 16 raw build-ID bytes, capability bits. Bits 0/1/2 mean wheel snapshot / command expiry and latch / boot+epoch+sequence command gate respectively; reserved bits zero. Build ID is a build artifact identifier, not its hex SHA-256. A receiver must demand the needed bits and supported version. Unknown function, no response, timeout, a legacy packet or malformed response = **unsupported/unknown**, never inferred support. There is no nonce or transaction ID in the query; only use it under exclusive UART ownership with bounded reads and explicit stale-frame handling. CRC is corruption detection, not authentication.

## Commands

Payload `<BB16sQIHB` plus `count` entries `<Bf`: type `02`, action, boot ID, unsigned 64-bit epoch, unsigned 32-bit seq, TTL milliseconds unsigned 16-bit, entry count; motor IDs are 0..3. ENABLE=1, UPDATE=2 require four unique IDs, TTL 1..500 ms, finite values; ENABLE requires all signed-zero values. STOP=3 requires count 0, TTL 0, current boot/epoch, strictly newer seq and enabled state. RELEASE=4 clears the fault latch only when not enabled and requires a strictly newer epoch. No partial updates; invalid length, count, ID, duplicate, NaN, Inf, zero/oversize TTL or stale/wrong boot/epoch/sequence is rejected without refreshing TTL. Sequence numbers are strictly increasing within epoch, not necessarily contiguous: the upper latest-wins queue can discard an older target without turning that discard into a fault. Replayed or backwards sequences are rejected; seq does not wrap. ENABLE requires stopped/latched state and an epoch greater than every accepted epoch for that boot; epochs cannot wrap. After STOP or timeout, a fresh greater epoch plus a zero ENABLE is required. Nonzero targets follow only in a later UPDATE. A valid command has no execution ACK; sending bytes is not execution evidence.

TTL is **remaining duration at MCU receipt**, never a cross-host absolute monotonic timestamp; upstream must subtract queue/transit residence and reject when remaining <= 0. Serial transmission and board scheduling latency still need bounding. Periodic expiration independent of traffic sets all targets zero and latches STOPPED + TIMEOUT. TTL changes must be atomic with the four targets relative to the 10 ms control ISR; expiration must apply the zero targets even when a concurrently received command is rejected. `t2_expire()` and `t2_command()` require serialization by their caller. SysTick wrap uses modulo 32-bit comparison and expiry must run at least once within 2^31 ms. Values are PID setpoint RPS, subject to existing per-motor safety limits in the eventual integration; this candidate does not apply them. Rejected frames cannot reset the deadline.

## Snapshots

Payload `<B16sIII` plus 4 entries `<qff` in motor-ID order 0,1,2,3: type `82`; boot_id; board monotonic tick_ms (wraps uint32), sample sequence (uint32), faults (uint32); then signed int64 total encoder counts, measured RPS and actual applied target RPS. Payload is 93 bytes, entire frame 98 bytes. Fault bit 0 = timeout, bit 1 = stopped; reserve other bits. A snapshot's validity is established by the receiver only after capability, correct boot, finite RPS, frame integrity, sample order/freshness, and hardware-specific calibration and channel health checks. Do not label an unknown initialization, timer miss, invalid encoder, or absent hardware as a valid zero measurement. The initial coordinate and wheel order/signs require independent calibration.

Acquire a coherent copy at the motor update boundary: all four counts, filtered measured RPS, applied setpoints, tick/seq and faults from one update. Copy under an appropriately bounded critical section into a buffer; serialize and send from a task, never blocking in an ISR. Account for encoder wrap pending at sampling, interrupt priorities, direction reversals, atomic 64-bit reads, sequence/tick rollover, and overflow of 64-bit totals. Existing ARR=60000 means hardware modulus 60001; the two-line isolated patch corrects this constant and the fourth timer start but **does not solve pending-wrap races or prove snapshot consistency**. Counts/rps in fixtures are illustrative, not hardware observations.

`golden_vectors.json` has capability, enable/update/stop, sample, 59999→60001 count wrap, changed boot, wrong function, bad CRC and empty legacy response. The changed-boot frame is structurally valid: an established session must invalidate old samples and renegotiate/re-enable; it is not a malformed wire packet. Decode wrong-function and CRC vectors as rejects; do not use any vector as proof a board supports the protocol.

## Integration gates

- Generate a genuinely fresh boot ID across software resets **and power loss**; device UID alone or volatile tick zero is not fresh. Define behavior if entropy/persistence fails: remain disabled and advertise no unsafe capability. This work has not selected or verified a board-specific source.
- Resolve the legacy MOTOR command path so it cannot bypass the latch and watchdog, while preserving intentional compatibility only under an explicitly designed safe mode. The vendor parser and task access must be bounded and concurrency-reviewed. The standalone module is not called by the original firmware.
- Resolve lazy motor initialization and allocation failures, timer interrupt ordering, pending overflow, coherent snapshots, and ensure the existing limit function is respected. The original task startup invokes `set_chassis_type` before lazy `motors_init`, which may dereference null pointers. Do not deploy either partial artifact alone.
- Wire periodic expiry into a scheduling path that remains active when UART stalls. IWDG refresh does not implement communications timeout. Target zero is not evidence of physical stop: PID, inertia, power state and load require real validation.
- Add the source to the actual Keil project, assign a reproducible build ID, construct an isolated exact-source build, review warnings and produce a fresh hex + SHA-256. Preserve a known-good on-device image and separately authorized rollback plan; no flashing is authorized in this wave.

The proposed command payload does **not** carry the section 3 logical `source` or a cryptographically authenticated owner. The firmware candidate cannot reject a packet merely because it originated from the wrong upstream source; the serial-owner gateway must enforce that logical source before forwarding, and exclusive bus ownership itself must be established separately. This is an explicit interface limitation for coordinator review, not an implemented wrong-source security guarantee. The proposed protocol is not final until that decision is made.
